## 2. 产品定位与责任边界

Climate Passport，简称 CP，是跨项目、跨活动、跨机构、跨国家的身份、行动证据与能力资产核心平台。

CP 提供可直接使用的用户端、可运营管理的后台，以及供第三方调用的 Open API。用户的学习、实践、参与和贡献记录构成长期能力与行动的来源。

| 系统类型 | 责任范围 |
| --- | --- |
| CP 自营业务 | CP 管理身份及自营项目的申请、审批、参与、完成、凭证和奖励全流程 |
| SHCW 等 Channel Shell | 管理品牌与内容展示，通过 CP API / SDK 使用 Core 能力，不重复建设 Core 业务 |
| 独立第三方系统 | 管理自己的界面、账户密码、业务数据、后台、审批和运营流程；向 CP 提交授权范围内的关键事实，并调用约定的 CP 能力 |

### 2.1 CP Core

- 管理 CP 身份、账户、Passport ID、隐私授权、凭证、积分账本、成就、徽章、里程碑、QR、Verifier、验证和 CP 参与记录。
- 管理 CP 自营及薄壳模式下的报名、申请、审批、签到与完成流程。
- 对独立第三方提交的数据执行权限校验、身份关联、事实接收、证据评估和奖励判定。
- 管理机构与活动的可信评定、奖励策略、来源追溯、纠错、撤销和审计。
- 不接管独立第三方的内部审批、人员运营和与 CP 无关的业务状态。

### 2.2 SHCW Shell

- SHCW 继续作为 Channel Shell，管理 CMS、新闻、议程展示、活动页面、人物展示、媒体中心、合作伙伴展示与 SHCW 品牌。
- SHCW 调用 CP 的身份、报名、签到、学习申请、证书和奖励等 Core 能力。
- SHCW 展示用的人物与机构信息消费 Core 主数据的授权读模型。
- 不将所有第三方系统统一归类为 SHCW 式薄壳。

### 2.3 独立第三方系统

- 独立第三方必须拥有支撑其业务的数据持久化与管理能力；可以采用自建系统、CMS、LMS、SaaS 或托管后台，不要求每个项目自建物理数据库。
- 人员注册、项目报名、业务审批、课程教学和项目执行保留在第三方自己的界面和系统中。
- 第三方业务操作不得以跳转 CP 页面为前提；通过 API 完成与 CP 有关的信息流转和能力调用。
- 用户以后主动进入 CP 激活账户、查看 Passport 或管理隐私，不构成第三方业务流程的强制跳转。

## 3. 九大功能体系

每个功能体系必须同时定义用户可用功能、管理端运营能力和受权限控制的 Open API。对外开放不等于公开所有数据，也不等于授予第三方平台管理员权限。

| 功能体系 | 用户端 | 管理端 | Open API |
| --- | --- | --- | --- |
| 身份与信任 | 注册登录、Passport、账户安全、隐私与来源关联 | 用户、机构、角色、授权、身份核验与安全记录 | 同意开通 CP、身份关联、必要资料读写、授权和状态查询 |
| 能力资产 | 行动时间线、能力档案、证据来源、授权展示与导出 | 来源、证据、评估、纠错和资产状态 | 行动记录提交、证据引用、更新撤销、授权档案查询 |
| 学习成长 | 课程发现、学习记录、进度、完成凭证 | 课程来源、学习标准、同步状态、成果与奖励 | 课程目录、选课、进度、测评、有效学时和完成结果 |
| 活动与实践 | 活动发现、参与记录、签到、实践与角色贡献 | 自营活动全流程、第三方事实、核验和统计 | 活动目录、确认报名、CP 签到、参与时长、完成与贡献记录 |
| 社区与挑战 | 社区、群组、挑战、交流、进度和榜单 | 内容治理、挑战配置、规则与异常处理 | 授权参与、挑战进度、行动成果和允许公开的内容 |
| 招聘与协作 | 职位与项目发现、申请、授权能力展示 | 自营机会管理、机构需求、授权及协作记录 | 职位和项目目录、授权能力查询、合作成果记录 |
| 成就与激励 | 徽章、等级、任务、目标和里程碑 | 定义、规则、授予、审核、撤销和历史 | 合格事实触发、授予状态、徽章及成就查询 |
| 积分与兑换 | 积分钱包、流水、兑换和订单结果 | 积分规则、额度、对账、冲正和风险管理 | 余额、预占、确认扣减、释放、冲正与兑换状态 |
| AI 服务 | 学习建议、行动建议、资料提取、机会匹配和内容摘要 | 模型权限、来源、质量反馈、人工纠正与运行记录 | 授权范围内的分析任务、处理状态、结果和反馈 |

### 3.1 学习与实践

- 课程引擎优先对接现有 LMS；Tutor LMS 为基础需求中的课程集成对象。CP 不重复建设完整课程引擎。
- 课程购买、第三方教学和订单流程由对应系统管理；CP 接收必要的学习与结果信息。
- Learning Experience 保持独立的 Program / Application / Participation 领域，不合并为普通 Event。
- CP 自营 Learning Experience 保留自身申请、评审和录取流程；外部机构仅同步授权范围内的最终参与、完成和成果事实。
- 有效学时、完成标准与测评依据必须可追溯；报名不等于学习完成，签到不等于能力认证。

### 3.2 能力资产与 AI

- 能力档案覆盖学习力、行动力、创新力、组织力和影响力，并关联相应事实与证据。
- 人员、课程、活动、实践、贡献、凭证与能力标签之间保留可追溯关联。
- AI 输出属于建议、提取或辅助评估，不直接替代身份核验、可信评定或正式发证规则。
- AI 数据使用受用户授权、来源权限和隐私范围约束，支持人工纠正。

### 3.3 积分与外部商城

- CP 管理自身积分账本；外部商城管理商品、支付、订单、履约和售后。
- 消耗 CP 积分必须通过 CP 的余额检查、预占、确认扣减、释放及冲正机制。
- 第三方不得先完成兑换，再以普通记录写入方式要求 CP 扣分。
- 退款、取消和撤销必须同步影响积分与相关奖励，保留原始交易及补偿流水。

## 4. 第三方注册与 CP 身份开通

### 4.1 用户同意

1. 第三方注册表单提供独立的“同时注册 Climate Passport”选项，默认不勾选。
2. 明确告知 CP 接收的数据、用途、条款和隐私说明。营销订阅与公开档案授权单独处理。
3. 用户拒绝时，不通过该流程创建 CP 身份或上传其可识别的个人履历，不影响第三方服务使用。
4. 同意记录包含来源合作方、第三方人员引用、明确选择、时间、条款版本、数据范围与用途。

### 4.2 开通结果

- 第三方通过服务端 API 提交必要资料、稳定人员引用和同意证据。
- CP 为符合条件的新身份创建非公开、待认领的 Passport 档案，并分配稳定 Passport ID。
- 建立 Passport 档案不等于完成身份核验、获得登录会话或开放个人资料。
- 未完成身份关联的第三方记录保存为受限的待关联记录，不公开、不自动形成已核验的个人奖励。
- 重复请求不得生成重复 Passport、重复记录或重复注册奖励。

### 4.3 密码与首次访问

- 第三方独立管理第三方密码；不得向 CP 发送密码或密码哈希。
- CP 不创建默认密码，不发送明文初始密码，不允许合作方使用集成凭据设置或重置 CP 密码。
- 首次访问提供“激活 Passport / 首次设置密码”入口，由 CP 验证联系方式归属后设置独立密码。
- 已有密码使用找回并重置流程；未设置密码使用认领与首次设置流程。共享安全组件不得混用操作权限或跳过状态校验。
- 修改任一系统的密码，不改变另一系统的密码。
- 验证凭证必须限时、单次使用、绑定账户与操作，安全存储并防止重放、暴力尝试和账户枚举。
- 验证与状态变更必须具备并发保护；不得绕过冻结、停用或 MFA 限制。

### 4.4 已有账户与跨来源关联

- 已有 CP 身份在验证授权后关联，不重新创建身份，不覆盖原密码、角色、资料或安全设置。
- 邮箱相同只是关联候选，不是自动合并、读取档案或挂接记录的授权。
- 未验证的请求不得向第三方泄露账户存在性、现有 Passport ID 或无关个人信息。
- 保留合作方与人员的稳定映射；并发注册、重复通知和跨合作方关联必须收敛到正确身份。
- 用户可以查看关联来源、拒绝异常关联、撤回后续同步授权。保留和删除按已批准的数据政策执行。

## 5. 关键事实、证据与记录生命周期

### 5.1 接收范围

CP 接收授权范围内的身份关联、已确认报名、角色、签到签退、有效参与时长、学习进度、测评结果、完成成果、实践贡献、证据及相关纠错撤销。

第三方内部审批意见、未获确认的业务流转、无关申请材料和管理备注不默认同步到 CP。

第三方审批完成后提交 Confirmed 或等效的确定结果；CP 不重复执行第三方审批，但必须校验接口权限、身份关联、数据有效性及 CP 接收规则。

### 5.2 最小记录要素

- 来源合作方及来源机构。
- 第三方唯一记录引用、人员映射和项目／活动／课程引用。
- 事实类型、状态、角色及与该事实相关的结果字段。
- 发生时间、接收时间、记录版本。
- 证据引用、验证方法、授权范围和可见范围。
- 处理回执、变更关系、纠错或撤销状态。

来源合作方由有效凭据确定，不采信请求正文中可任意伪造的合作方身份。

### 5.3 生命周期

- 区分已接收、待关联、待核验、已确认、已纠正和已撤销等业务状态；具体状态模型须在接口与数据库设计中统一。
- 接收来源事实、认定证据、判定奖励资格和实际发奖是独立步骤。
- 每项能力与奖励必须能追溯到来源事实、证据和适用规则。
- 支持更正、取消、撤销、重试和重放检查；不得以“最终数据”为由禁止后续纠错。
- 不通过覆盖或删除历史记录掩盖状态变化。

## 6. 机构与活动可信体系

### 6.1 独立评定

| 维度 | 管理要求 |
| --- | --- |
| 机构可信等级 | 记录机构身份、评定范围、证据、评定人、有效期、复核时间、版本与停用状态 |
| 活动可信等级 | 独立评定具体项目／活动／期次的标准、核验方式、完成要求、证据质量和可审计性 |
| 个人成果证据 | 验证具体人员的实际参与、有效学时、任务完成、测评或贡献，不以机构或活动等级替代个人证据 |

- 高可信机构的所有活动不自动获得最高等级。
- 可信活动的所有报名者不自动获得参与或完成认定。
- 机构可信等级、API 权限、核验权限和发证资格分别管理。
- 不以赞助金额、知名度或商业合作关系直接确定可信等级。
- 机构身份验证不等于取得学术、专业或法定认证资质。

### 6.2 管理能力

- 后台提供机构评定、活动评定、证据审核、复核提醒、暂停、降级、恢复与申诉管理。
- 每次评定及调整保留操作者、时间、范围、证据与版本。
- 对外仅返回调用方有权查看的等级状态、适用范围和奖励结果，不公开内部风险或审核备注。

## 7. 可信等级与奖励规则

奖励资格共同取决于：机构可信等级、活动可信等级、身份关联、个人证据、发证／授予权限及生效中的奖励规则。

| 已满足条件 | 奖励边界 |
| --- | --- |
| 仅提交来源声明 | 保存待核验事实，不自动颁发已认证奖励 |
| 已确认报名 | 形成报名记录，不作为出席、完成或能力证明 |
| 已核验参与 | 按规则获得参与类证书、徽章或积分 |
| 已核验完成或能力成果 | 按对应标准获得完成类／能力类凭证及配套奖励 |

- 不同可信等级可以对应不同证书类别、积分额度、徽章资格、自动发放权限和人工审核要求。
- 高等级不等于所有行为都获得更多积分，不以通用倍数替代具体规则。
- 规则支持适用范围、证据条件、奖励定义、额度、上限、重复限制、生效时间和审核要求。
- 规则须可版本化、预览、审批发布并审计；授予时保存评定、证据和规则快照。
- 同一事实重复提交不得重复发奖；人工例外须有授权、依据和审计。
- 新规则默认向后生效，不静默改写历史证书或积分。
- 来源异常或机构停用时，暂停相关新增自动授予并启动影响评审；不得无条件批量否定所有历史成果。
- 确认无效的事实须追踪受影响的证书、徽章和积分，执行有依据的撤销及补偿流水。
- 积分已消费时，按批准的追偿和账户限制政策处理，不删除原始流水。

## 8. Open API 与 SDK

### 8.1 必备能力

- 合作方接入、应用身份、权限范围、密钥管理和停用。
- 同意开通 CP、人员关联、关联状态及授权撤回。
- 项目、活动、课程和公开内容目录同步。
- 已确认报名、学习、实践、贡献与证据的提交、更新和撤销。
- CP QR、签到、Verifier 和凭证验证能力。
- 经授权的 Passport 记录、奖励结果、证书和积分查询。
- CP 积分预占、确认、释放与冲正。
- 异步处理回执、通知、Webhook、重试和对账。

### 8.2 接口约束

- 第三方不得直连 CP 数据库写入记录、积分或凭证。
- API 身份、机构范围、项目范围和用户授权共同约束访问；不得跨机构或跨人员越权。
- 写操作具备幂等性，异步接收先持久化再确认，支持乱序、版本冲突、重试和补偿。
- Webhook 必须可验证来源、防重放并支持可靠重试；回调仅传输允许范围的数据。
- 服务端密钥不得进入浏览器、原型文件、日志或公开 SDK 配置。
- API 具备版本、字段定义、错误语义、分页、限流、审计和兼容策略。
- SDK 复用公开契约，不绕过服务端授权；内部页面接口不得未经接入验收直接作为第三方接口发布。
- 第三方可读取允许范围内的处理结果，不能自行指定 CP 权威可信等级或绕过奖励规则。

## 9. 公开内容与双向导流

- CP 官网提供第三方活动、课程、项目、新闻和机会的发现入口。
- 接收获授权公开的标题、摘要、时间、地点、分类、发布机构、语言、来源链接及更新状态。
- 访问来源项目并在第三方界面办理报名、学习和参与；相关授权成果通过 API 回到 CP。
- 保留来源标识和原文链接，支持更新、下架和撤回，执行必要的内容管理。
- 内容目录与私人参与记录分开存储、授权和展示。
- 新闻发布、目录收录和浏览行为不得直接冒充已认证参与或能力成果。

## 10. Passport ID、QR 与公开验证

### 10.1 Passport ID

- 格式固定为 `XXXXXXX-XXXXXX`：无前缀，13 位随机大写 Crockford Base32 字符，按 7 + 6 展示。
- 排除 `I`、`L`、`O`、`U`；使用安全随机生成、唯一约束及碰撞重试。
- 全球唯一、长期稳定、非顺序、不可预测；不编码年份、地区、角色、活动、来源或注册顺序。
- 内部主键保持 UUID/CUID；公开 Passport ID 不是登录凭据或记录修改授权。

### 10.2 QR 与 Verifier

- 默认采用 opaque token；不得包含个人信息、原始 JSON、邮箱、电话或内部数据库 ID。
- 证书 QR 使用公开验证 URL 与不透明验证码，长期有效并支持服务端撤销。
- 活动签到 QR 使用短期 token、强制有效期、服务端校验和审计；签名用于增强防篡改，不替代服务端判定。
- Passport QR 使用受隐私设置约束的公开资料 URL 或受控 token。
- 邀请／特殊通行 QR 具有明确有效期、访问规则、次数限制及撤销能力。
- QR 展示形式不能作为事实依据；由服务端解析并返回授权视图。
- Verifier 集成在 CP Core，独立暴露 API，不单独拆为 App；核验人员权限、活动规则和签到结果由 Core 管理。
- 当前不开发离线 QR 认证。

### 10.3 公开凭证展示

公开验证只核验证书，不公开完整个人档案。

允许字段：验证状态、证书标题、证书印载姓名、脱敏 Passport ID、颁发机构、签发日期、适用的有效期、凭证类型、关联项目／活动、证书编号、验证时间。

禁止字段：邮箱、电话、证件号、出生日期、申请材料、内部用户 ID、管理员备注、完整个人资料及私人 Passport 记录。

## 11. 核心数据与工程边界

- Person 与 Institution 为长期 Core 主数据；SpeakerProfile、MentorProfile、ExpertProfile 为角色档案。
- EventSpeakerAssignment 表示活动人物关系；InstitutionRole、PartnerRole 表示项目级机构关系。
- 同一人物与机构支持 CP、GCA、SHCW、Learning Experience、证书、公开资料及后续 AI 匹配复用。
- 第三方人员和机构使用映射关联 Core 主数据，不将渠道局部资料直接覆盖为全局权威信息。
- Web、Admin、API、公开 Verify 分离职责和访问权限；已有单应用结构按阶段演进，不将目标结构描述为已完成部署。

目标代码结构：

```text
apps/passport-web
apps/passport-admin
apps/passport-api
packages/passport-core
packages/passport-contracts
packages/passport-sdk
packages/passport-ui
```

- Core 统一承载业务规则；契约、SDK 和 UI 不各自重写身份、签到、积分或证书逻辑。
- 保留已存在的身份、参与记录、证书、积分和关联连续性；迁移具备数据校验及回退方案。

## 12. 前端、后台与隐私要求

- 用户端提供真实数据、完整操作、加载、空状态、错误、重试及无权限反馈，不能以静态原型代替功能完成。
- 管理端提供可执行的管理、审核、配置、追踪、导出权限控制和异常处理，不仅提供展示页。
- 后台采用统一模块导航，相关模块提供子菜单；展示权限与服务端权限同时生效。
- `ui-prototypes/` 为持续更新的页面原型目录。除 hero 和 footer 外，信息一致时尽可能复现其版面、层次、交互和视觉设计。
- 数据结构、状态流转、权限和业务规则独立遵循本文及专项契约，不照搬原型中的示例数据或业务假设。
- 首期完整覆盖简体中文和英文，其他语言按专项计划扩展；界面、通知、目录和 API 语言字段保持一致。
- 默认最小必要收集和最小可见范围；公开档案、资料共享、第三方同步和营销授权分别管理。
- 提供隐私设置、来源关联管理、授权撤回及适用的数据导出和删除流程。
- 敏感字段按权限展示，日志不保存密码、完整认证 token 或不必要的个人资料。

## 13. 开发执行顺序

| 顺序 | 交付范围 | 完成门槛 |
| --- | --- | --- |
| 1 | 权限与来源边界、合作方契约、字段及状态定义 | 核心规则明确；现有安全问题不因外部接入而被绕过 |
| 2 | 同意开通、待认领档案、首次设密、已有账户关联 | 无密码同步、无接管漏洞、无重复身份 |
| 3 | 首个合作方的活动与记录闭环 | 确认报名、CP 签到、来源留痕、查询、纠错和对账通过验收 |
| 4 | 机构／活动可信评定与奖励规则 | 后台可管理，规则可版本化，授予与撤销可追溯 |
| 5 | 学习实践、证书、徽章、积分与用户档案联动 | 前端可用、后台可管、第三方接口可调用 |
| 6 | 内容导流及其余功能体系分阶段完善 | 对应模块的界面、运营、API 和验收同步交付 |

九大体系均属于产品目标；按上述顺序分阶段交付，不将全部目标视为首期同时上线要求。

## 16. 验收标准

1. 用户不选择同时注册时，不通过该流程创建 CP 身份或传输个人履历。
2. 同意后可创建待认领 Passport；首次设密完成身份验证，第三方密码始终不进入 CP。
3. 已有账户不会被同邮箱请求接管、覆盖或未经授权关联；重复及并发请求不制造重复身份。
4. 第三方保留自己的 UI 和审批流程，使用 API 完成确认报名、签到及成果回传，不强制跳转 CP。
5. 每条记录与每项奖励均可追溯到来源、身份关联、证据、规则和处理历史。
6. 机构等级、活动等级与个人证据独立生效；报名不直接变成完成证明。
7. 相同事实在不同已批准策略下产生相应奖励，重复投递不重复发奖。
8. 纠错、撤销、机构停用和规则更新有明确处理流程，不静默覆盖历史奖励。
9. 接口具备隔离、授权、幂等、重试、限流、审计和对账验证；公开接口不泄露私人记录。
10. 用户端可操作、管理端可运营、第三方接口可联调；测试和实际环境证据与完成状态对应。
11. 公开验证遵循最小披露，QR 始终由服务端验证。
12. 当前版本不依赖链上能力或离线 QR 认证。
