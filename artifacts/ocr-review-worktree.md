With two concurrent processors, worker B claims 0 rows but still sees all of worker A's freshly-claimed PROCESSING rows here and delivers them a second time, defeating the lease and duplicating external callbacks. Claim per-row (single-row `updateMany` CAS and skip on count 0) or tag the lease with an owner token and filter the re-fetch by it.
- **[medium]** Two state-machine gaps here: (a) the update unconditionally sets `status: SUCCEEDED`/`deliveredAt`, so reconciling a DEAD or still-PENDING dispatch silently resurrects it as delivered; (b) the idempotency check reads `stored.receipt`/`stored.reconciledRevision`, but the success path in `processOutboundDispatches` stores receipts in a different shape (`{ httpStatus, body, receivedAt, revision }`), so after a real delivery `sameReceipt` never matches and a reconcile overwrites the original delivery receipt — destroying the evidence this module exists to keep. Normalize one receipt shape for both paths and only allow reconcile transitions from SUCCEEDED (or explicitly handle DEAD/PENDING).
- **[low]** `callbackUrl` is validated as https-off-localhost at registration (`validateCallbackUrl` in channel-client-auth.ts), which is good — but `fetch` follows redirects by default, so a validated https callback can 302 the worker to `http://169.254.169.254/...` or other internal addresses, keeping an SSRF primitive alive via redirect. Use `redirect: "manual"` (treat 3xx as a non-retryable or dead-letter response) or re-validate every redirect target before following.
- **[low]** `DispatchRow` omits `idempotencyKey`, forcing this ad-hoc cast `(row as { idempotencyKey?: string })` even though the field always exists on the fetched row — add it to the `DispatchRow` type instead of weakening type safety. Related edge case in the same file: `canonicalize` maps `undefined` values to `"null"`, so `{ a: undefined }` and `{ a: null }` produce identical payload hashes; worth documenting or normalizing explicitly since the hash guards idempotency conflicts.
- **[low]** The migration mixes idempotency styles: `CREATE TABLE IF NOT EXISTS` is used, but `ALTER TABLE "channel_clients" ADD COLUMN "callbackUrl"` and all three `CREATE INDEX`/`CREATE UNIQUE INDEX` statements lack `IF NOT EXISTS`. After a partial failure the migration cannot be re-run, unlike the sibling notification migration which uses `ADD COLUMN IF NOT EXISTS`. Add `IF NOT EXISTS` consistently (column and indexes) to keep the migration re-entrant.
- **[low]** Inconsistent idempotency within this file: the `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS` for notifications are re-entrant, but the two `privacy_markers` indexes use plain `CREATE INDEX` (while the table itself uses `CREATE TABLE IF NOT EXISTS`). A partial failure after the table is created makes re-running the migration fail on these two statements. Add `IF NOT EXISTS` to both `CREATE INDEX` statements for consistency.
- **[low]** The `matches` helper uses loose comparisons (`row[key] != null`, several occurrences), which violates the project's strict-equality rule (`!==`/`===` required). The same pattern exists in tests/reliable-dispatch.test.mjs. Since these are deliberate null/undefined guards, rewrite them explicitly (e.g. `row[key] !== null && row[key] !== undefined`) to keep test code consistent with the codebase standard.
